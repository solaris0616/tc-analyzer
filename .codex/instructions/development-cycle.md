# Software development cycle

ソフトウェア変更は、次の工程を順番に通します。小さな変更でも工程を省略せず、レビューの深さだけをリスクに応じて調整します。

## 1. 要求整理

1. ユーザー要求を、観測可能な受け入れ条件へ変換する。
2. 変更対象、変更しない対象、破壊的変更、データ再構築要否を明確にする。
3. リポジトリと設計資料から確認できる内容は質問せず調査する。
4. ユーザーの明示的な方針を、推測した追加要件で上書きしない。

## 2. 設計

1. 関連する`design/*.md`を先に読み、変更後のデータフローと不変条件を定める。
2. DB、API、CLI、ダッシュボード、エクスポート、テストへの波及を列挙する。
3. 設計資料は変更後の現在形で更新する。変更履歴との比較や、実装済み事項を将来形で記述しない。
4. 設計完了後、新しい`independent_reviewer`へ設計レビューを依頼する。レビュー担当は編集しない。
   起動前にread-only権限を指定・確認する。実行環境で保証できない場合は編集禁止を明示し、レビュー前後の`git status --short`を比較する。
5. 指摘が妥当なら修正し、別の新しい独立レビューでクリアされるまで実装へ進まない。

## 3. 実装

1. 承認された設計と受け入れ条件の範囲内で実装する。
2. データの保存前に終了条件や拒否条件を評価し、無効な行を永続化しない。
3. 永続化形式を変更したら、スキーマ、型、SQL、スキャン処理、API、CLI、UI、エクスポート、資料を一緒に更新する。
4. 実装完了後、新しい`independent_reviewer`へ実装レビューを依頼する。
5. 指摘修正によって設計や挙動が変わった場合は、設計レビューから影響工程をやり直す。

## 4. テストと検証

1. 正常系だけでなく、境界条件の組み合わせ、状態遷移、複数セッション、カウンター減少、重複、キャンセルを検証する。
2. `mise run fmt`で整形する。
3. 開発中の対象テストを実行し、工程完了時は`mise run verify`を実行する。
4. テスト完了後、新しい`independent_reviewer`へテストレビューを依頼する。テストが実装の追認になっていないか、重要な組み合わせが抜けていないかを確認させる。
5. 指摘が妥当ならテストまたは実装を修正し、必要な工程と独立レビューを繰り返す。

## 5. 最終レビュー

1. 要求、設計、全差分、テスト結果を、新しい`independent_reviewer`へ渡す。
2. 最終レビュー担当はファイルを編集せず、親エージェントの結論を前提にしない。
3. 指摘を修正した場合、最低でも`mise run verify`と新しい最終レビューを再実行する。
4. 「全指摘クリア」が得られるまで完了扱いにしない。
5. ユーザーへの完了報告には、変更結果、重要な挙動、検証コマンド、独立レビュー結果、残存リスクを含める。
