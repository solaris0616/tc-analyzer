# Independent review

独立レビューは設計、実装、テスト、最終差分の各工程で、新しいレビュー専用エージェントが行います。

## Independence

- レビュー担当は対象の設計・実装・テストを編集しない。
- レビュー担当は`read-only`サンドボックスで実行する。
- 親側の権限指定がエージェント定義を上書きし得るため、起動時にread-onlyであることを確認する。保証できない環境では編集禁止を明示し、開始前後の`git status --short`を比較する。
- 親エージェントの「問題なし」「修正済み」という結論を証拠にしない。
- 要求、現在のファイル、実行結果、差分から独自に判断する。
- 前工程と同じエージェントを再利用せず、新しいレビューセッションを起動する。

## Review priorities

1. 正確性、停止条件、永続化不変条件、データ損失
2. 状態条件が同時成立する場合の判定順序
3. SQLの構文、パーティション、順序、NULL、減少・リセット
4. DB変更のCLI、API、UI、エクスポートへの波及漏れ
5. 設計資料のシグネチャ、全フィールド、全テーブル、索引、ルート、SQL
6. テストの境界条件、複数セッション、重複、キャンセル、エラー経路
7. セキュリティ、秘密情報、破壊的操作

## Stage-specific focus

- 設計レビュー: 受け入れ条件、データフロー、不変条件、波及範囲、実装可能性
- 実装レビュー: 実行経路、判定順、SQL、エラー処理、並行処理、資料同期
- テストレビュー: 失敗を検出できるアサーション、組み合わせ条件、キャッシュなし実行
- 最終レビュー: 要求から資料・実装・テスト・公開形式までの一貫性

## Validation

- 可能なら`mise run verify`を実行する。
- 実行できない検証は未確認として明示する。
- ファイルを変更して検証を通してはいけない。
- レビュー開始時のワークツリー状態を記録し、終了時に意図しない差分が増えていないことを確認する。

## Output

- 指摘を重要度順に並べる。
- 各指摘に`P0`から`P3`、絶対ファイルパス、狭い行番号、影響、根拠を付ける。
- スタイルのみの指摘は原則として省く。
- 問題がなければ「全指摘クリア」と明記し、残存リスクだけを報告する。
